No application changes, builds, database connections, migration execution, activation or remote operations were performed. Untracked AGENTS.md, CLAUDE.md and error.log were preserved.

## Product conclusion and launch boundary

BASOUL is an organization-aware business workspace with substantial working Web functionality and a narrower Android companion. Projects, tasks, CRM, content planning, knowledge, finance tracking, activity and notifications have actual data/UI implementations. Engineering includes a real CAD ingestion service, semantic geometry pipeline, 2D/3D viewer/editor and persisted scenes, plus a separate PDF/image analysis/review workflow. It is not merely a dashboard mock-up.

However, functional breadth exceeds integration completeness. Task transitions/edit/archive are the strongest locally verified journey. Other paths mix active-organization APIs, first-membership fallback and direct Supabase calls. Navigation, multi-step mutations and non-task audit integrity need focused completion. No whole-product production readiness or credible overall completion percentage can be inferred from passing local tests.

Shortest safe launch: a controlled **Web pilot for one isolated organization**, with owner onboarding, invitations, projects, tasks, project files/notes and an in-app inbox. Start with Web; Android follows as an explicitly scoped companion for existing members, tasks and review actions. Do not require Mobile parity with finance/CRM/content before this pilot. Engineering may join the pilot only after its own gateway/storage/tenant journey passes; otherwise disable its unsupported entry points and APIs for pilot users instead of presenting an unavailable feature. Finance can remain a tracker only if history/permission tests pass and it is not marketed as accounting. Content is planning, not automatic publishing.

## Architecture that actually exists

- **Web:** Next.js App Router; business modules largely embedded in `app/page.tsx`; dedicated authentication, administration/settings and architecture routes. Shared YVL UI, i18n and workspace shell components.
- **Mobile:** Expo SDK 57 / React Native, one state-based screen router in `mobile/App.tsx`, Supabase session and revision-aware organization context. Task, notification and engineering-review services are real; projects are presently a read-only listing.
- **Backend:** Next authenticated business/architecture APIs, Supabase Postgres RLS/RPC/Storage and Deno functions for organization administration and architectural analysis. The Python FastAPI CAD gateway is a separate service, not a Next route implementation.
- **Shared packages:** task status/CAS/reason/notification contracts; platform registry/config/API envelopes; CAD normalization/semantic floor graphs; scene editing/reconciliation/persistence/IFC adapter interfaces; deterministic executive/decision engines; design tokens/adapters. Some overlapping Web/Mobile decision and domain models remain.
- **Data:** organization -> memberships/workspaces -> business rows and projects -> tasks/files/notes/drawings/reviews/findings/elements/comments/scenes. Clients link projects/content/finance; task findings and project notes can create tasks. Activity and notifications connect modules, but only the reviewed task paths have the demonstrated transactional protections.
- **Two workspace concepts:** the four Executive/Operations/Engineering/Knowledge UI modes are static presentation categories; `organization_workspaces` is a persisted API-backed entity. Do not describe these as one completed workspace lifecycle.

## Concrete broken or incomplete journeys

These are source-grounded findings and test targets, not claims of newly reproduced production incidents.

1. **Switch organization -> administer/settings/engineering:** Home has an organization selector, but administration/settings choose the first membership; architecture clients do not send x-yosseuf-organization and the server falls back to the first membership. The selected organization can diverge from the operation context. Fix the contract, not just a label. E02/E03/E16.
2. **Switch organization during a non-task edit:** selector clears task/project/notification state but not all business arrays/modals; remembered organization updates after load completes. Non-task writes lack the same operation snapshot guards as tasks. A stale action can target an earlier valid organization, even if RLS prevents unauthorized access. E08/E21.
3. **Delete finance in a non-first organization:** authorizedWorkspaceDelete omits organization header, so authenticatedDatabase falls back. Revalidate explicit scope for every delete; never infer success from an empty result. E21.
4. **Project note/finding -> task:** Web payloads omit organization_id, while IAM default_organization_id selects the first active membership. Task insert plus source-state update are separate transactions. Wrong-context rejection, duplicate tasks after retries or unlinked tasks after partial failure need tests and an atomic/idempotent contract. Do not invent broader assignment/actor permissions. E11/E17/E22.
5. **Project deletion with task history:** project cascade collides with preserve_task_history. Replace the destructive product promise with a safe archive/retention flow; do not weaken task protection. E07/E08.
6. **Find a record -> open it:** Web search discards record ID on selection; Mobile displays results without opening; ?view= registry links lead to Home's initial dashboard state. Make destinations explicit and test browser back/refresh and unavailable records. E18.
7. **Concurrent scene editing:** scene API upserts by organization/project without expected revision. Add conflict-safe saves before calling the editor collaborative. E16.
8. **File deletion/metadata and business audit failure:** storage and database writes are not atomic; task audit is stronger than ordinary module activity. Introduce recoverable states/idempotent repair and transaction-backed audited business mutations where integrity requires them. E10/E13/E14.
9. **Tasks available when engineering is unavailable:** Mobile loadMobileWorkspace throws on the first error from any of seven module reads. Optional engineering tables/service failures can block task use. Preserve fail-closed tenant authorization but isolate optional module errors. E23.
10. **Platform notifications API:** generic module-service sorts all resources by updated_at, whereas notifications use created_at. Existing task inbox success does not validate this alternate API. Add resource-specific metadata/integration coverage before consuming the platform registry more broadly. E06/E12.

## Architecture improvements without a rewrite

- Keep current Next/Expo/Supabase architecture and the tested task contracts. Introduce one explicit OrganizationContext passed through every user journey, server request and conversion; remove first-membership fallback for user-selected writes. Reuse Mobile revision invalidation semantics for Web non-task operations. UI selection is never authorization.
- Make resource metadata explicit: valid sort column, capability, route/record target, ownership rules and supported actions. Reconcile Documents/content naming and the two workspace concepts. Do not replace all navigation with a new framework just to add record targets.
- Expand shared domain types selectively: organization_id and opaque updated_at/version for relevant records, typed safe errors and AR/EN messages. Do not equate all business resources with task creator-only rules; preserve existing per-module RLS and test role outcomes.
- Move note/finding conversion and integrity-critical business writes behind scoped transaction/RPC boundaries with expected versions and an idempotency key. Reuse task patterns; do not copy its notification policy to every module without a product rule.
- Add module-level loading/error boundaries and bounded/paginated fetches. Web currently loads entire collections; Mobile loads all modules together with fixed limits. Distinguish empty, unauthorized, unavailable and truncated data.
- Consolidate overlapping executive calculations only after fixture parity tests expose meaningful differences. Keep deterministic recommendations labelled as such; do not upgrade scores into unsupported AI confidence claims.
- Preserve task audit/delete protections. Define archive/history access, project lifecycle, file retention and account removal together so deletion promises do not contradict data history.
