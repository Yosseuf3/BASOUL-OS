# Migration Phases

Every phase is independently approval-gated and stop-on-failure.

## Phase 0 — Planning & verification only

Freeze the inventory baseline, validate ownership, perform trademark/domain/account review, capture immutable identifiers, and rehearse rollback. No production mutation.

## Phase 1 — Documentation and non-runtime references

Update current documentation only. Preserve founder attribution and historical releases. Roll back through a documentation-only revert.

## Phase 2 — Visual branding in non-production environments

Use only approved locked BASOUL assets in isolated preview/staging surfaces. No Production alias, store build, or YVL modification.

## Phase 3 — Internal package/display naming

Introduce compatibility aliases before changing internal package scopes or manifest display identity. Require clean install, build, typecheck, and consumer verification.

## Phase 4 — Web production branding

Promote an immutable, prevalidated web artifact after rollback deployment and cache behavior are proven. Runtime business behavior must remain unchanged.

## Phase 5 — Mobile branding

Change approved display metadata only through signed release procedures. Bundle/package IDs remain protected by default. Retain legacy deep-link handling.

## Phase 6 — Domains and redirects

Add canonical BASOUL domains, TLS, DNS, Auth allowlists, analytics, sitemap, and redirects while old hosts remain live.

## Phase 7 — External services and integrations

Coordinate Vercel, Supabase display labels, gateways, stores, social accounts, monitoring, and legal records. Provider IDs and credentials remain unchanged.

## Phase 8 — Repository/project renaming

Rename repositories or governance projects only after clone URLs, Actions, webhooks, integrations, package registries, badges, and cross-repository links pass rehearsal.

## Phase 9 — Legacy YOSSEUF compatibility window

Keep old URLs, package aliases, headers, callbacks, and product labels operational with telemetry and published deprecation criteria.

## Phase 10 — Final deprecation

Remove only compatibility surfaces whose exit criteria, retention obligations, traffic thresholds, contractual review, and rollback windows are approved. Historical records remain immutable.
